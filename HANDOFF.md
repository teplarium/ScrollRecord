## 1. Суть продукта

**ScrollRecord** — бесплатное open-source десктопное приложение. Ядро на Rust, интерфейс на Tauri. Оно делает две вещи:

1. **Видео прокрутки сайта** на разных устройствах, от десктопа до телефона. Поверх рисуется **визуальный курсор** (на телефоне — касания), который показывает взаимодействие с сайтом.
2. **Запись отдельных анимаций сайта.** Старт и конец записи привязаны к блокам, а не к началу и концу страницы. Поэтому можно записать только анимацию hero-блока, только scroll-анимацию одной секции, только hover-эффект кнопки. Видео можно обрезать по границам блока, в том числе с прозрачным фоном.

Сценарий собирается на **канвасе в стиле FigJam**. Блоки сайта показываются карточками с настоящим содержимым сайта, стрелки задают порядок, овалы — старт и конец. Внутри блоков задаются задержки и взаимодействия с элементами. Сценарий хранится в **открытом JSON-формате**. ИИ может сгенерировать его по скиллу, который скачивается из приложения. Отдельный скилл есть и для **собственных курсоров**.

Видео выходит в стандартных пропорциях видеоредакторов: 16:9, 9:16, 1:1, 4:5 и т.д.

| D-32 | 2026-10-25 | Настройки компьютера не влияют на видео: всегда «полная анимация» (`prefers-reduced-motion: no-preference`) и светлая тема (`prefers-color-scheme: light`). Видео, которые сайт запускает сам, всегда запускаются (`--autoplay-policy=no-user-gesture-required`) | Один и тот же сценарий должен давать одно и то же видео на любом компьютере. Выбор тёмной темы в сценарии — позже (редактор / Фаза 4) |

Без Range видео нельзя перематывать. Без SPA-режима не открываются прямые ссылки React-приложений. Одной зависимостью меньше |
| D-34 | 2026-10-25 | Сторонние библиотеки тестовых страниц (GSAP, Lenis, lottie-web, React) лежат копиями в папке `vendor/` каждой страницы, с указанием лицензии | Тесты работают без интернета. | **Flow** | Сценарий записи: граф узлов и стрелок. Файл `*.srflow.json` |
| **Page (board)** | Страница сайта (URL). На канвасе — доска с полностраничным снимком, на ней выделяются блоки |
| **Block** | Смысловая секция страницы (hero, features…). Привязан к DOM-элементу через локатор. На канвасе — карточка с содержимым секции |
| **Node** | Узел графа: `start`, `block`, `navigate`, `end` |
| **Edge (arrow)** | Стрелка между узлами. Несёт настройки перехода: длительность или скорость скролла, easing, поведение курсора |
| **Anchor** | Точка привязки старта и конца внутри блока: `enter`, `top`, `center`, `bottom`, `exit` или `progress` 0–1 |
| **Action** | Действие внутри блока: hover, click, move, type, wait… |
| **Locator** | Способ найти элемент: `sr` (атрибут `data-sr`), CSS, текст, ARIA-роль, test-id. Хранится несколько вариантов |
| **Viewport** | Профиль устройства: ширина, высота, DPR, mobile/touch, user-agent |
| **Render target** | Что рендерим: вьюпорт + пропорции + разрешение + кадрирование + формат |
| **Aspect preset** | Пропорции итогового видео: 16:9, 9:16, 1:1… |
| **Fit** | Как сайт вписывается в кадр: `fill-viewport` (вьюпорт подгоняется под пропорции) или `contain` (окно сайта на фоне) |
| **Block clip** | Режим записи одного блока: кадр обрезан по блоку, запись анимации по времени или по скроллу |
| **Timeline** | Покадровый план, вычисленный из сценария |
| **Capture / Composition** | Захват «чистых» кадров страницы / сборка итогового кадра (страница + курсор + фон + эффекты) |
| **Cursor pack** | Набор курсоров: SVG-файлы состояний + JSON-манифест с hotspot и анимациями |
| **Site digest** | Сжатое описание сайта для ИИ |
| **Skill** | Пакет для ИИ: инструкции, схема, примеры |

## 4. Основные пользовательские сценарии

### 4.1 Промо-видео сайта (скролл)
1. **New project** → указать сайт: URL `localhost` (запущенный `npm run dev`) или **папку** со сборкой. Во втором случае приложение само поднимает локальный сервер.
2. Добавить **Render targets**: например, «Desktop 1920, 16:9, 1080p» и «iPhone 15, 9:16, 1080p».
3. Приложение снимает страницу и предлагает найденные блоки (MVP+).
4. На канвасе: Start (овал, привязан к блоку) → блоки-карточки → Navigate (если нужен переход) → End. Стрелки соединяют узлы, в панели свойств задаются задержки и действия.
5. Переключение устройства: блоки привязаны к DOM, поэтому раскладка пересчитывается сама. При необходимости добавляются переопределения (например, «на мобилке открыть бургер»).
6. **Preview** → **Render** → MP4 для каждого target.

### 4.2 Запись одной анимации (Block clip)
1. На канвасе выбрать блок → **Make clip**.
2. Выбрать тип: **Time** (страница стоит, пишется N секунд анимации блока) или **Scroll** (запись scroll-анимации от входа блока в экран до выхода).
3. Кадр: **по блоку** (видео ровно по границам секции, увеличение 1x/2x/3x). Фон: цвет или прозрачный.
4. Render → MP4, WebM с прозрачностью или PNG-секвенция.

### 4.3 Сценарий через ИИ
1. **AI → Download skills** (Flow skill).
2. Отдать модели скилл и одно из двух: **код сайта** (если модель работает с файлами проекта — Claude Code, Gemini CLI и т.п.) или **site digest** (для моделей без доступа к файлам).
3. Описать задачу словами → получить `*.srflow.json` → **Import** → валидация → доводка на канвасе.

### 4.4 Свой курсор
1. **Cursor Studio** → выбрать базовый пак → настроить размер, цвета, эффекты клика.
2. Или: скачать Cursor pack skill → попросить ИИ «сделай неоновый курсор с хвостом» → получить папку с SVG и манифестом → **Import pack**.
3. Или: нарисовать SVG самому (Figma, Illustrator) и собрать пак по шаблону.

## 7. Архитектура

### 7.1 Принципы
1. **Ядро без UI.** Вся логика в Rust-библиотеках. Tauri-оболочка и CLI — тонкие слои.
2. **Захват отдельно от композиции.** Браузер выдаёт «чистые» кадры, а курсор, фон, рамки и эффекты накладываются отдельно.
3. **Блоки привязаны к DOM, а не к пикселям**, поэтому один сценарий работает на всех устройствах.
4. **Сначала план, потом исполнение.** Сценарий заранее превращается в покадровый `Timeline`.
5. **Разъёмы через трейты:** `BrowserDriver`, `CaptureStrategy`, `Encoder`, `CursorRenderer`, `SiteSource`, в будущем `LlmProvider`.
6. **Один источник правды для типов.** Rust-типы → JSON Schema (для ИИ) и TypeScript-типы (для интерфейса) генерируются автоматически.

### 7.3 Как получается плавное видео

Запись экрана в реальном времени даёт рывки. Основной режим поэтому **покадровый**, с управляемым временем:

1. Время в браузере «заморожено» и на каждом кадре продвигается ровно на `1/fps`. Для этого инъецируется JS-шим (`requestAnimationFrame`, `performance.now`, `Date`, таймеры) и используется CDP-домен `Animation` для CSS-анимаций.
2. Скролл выставляется по таймлайну. Это настоящий скролл, поэтому срабатывают scroll-анимации, sticky-элементы и lazy-load.
3. В режиме `real` браузеру отправляется `mouseMoved`, и срабатывает `:hover`.
4. Кадр снимается (весь вьюпорт или область блока для Block clip).
5. Кадр уходит в композитор (сцена, fit, фон, курсор) и через pipe в ffmpeg.

Этот же механизм бесплатно даёт **Block clip**: пропустить интро (`warmup_ms`), записать ровно N секунд анимации, обрезать по блоку.

Режим **Realtime** (CDP screencast) используется для превью и Live-блока.

> ✅ Главный технический риск проверен (Фаза 1б, ADR 0004): статичный лендинг, CSS-анимации и переходы, GSAP + ScrollTrigger, Lenis, React SPA, страница с `<video>`, Lottie, canvas/WebGL и GIF. Пришлось изменить управление анимациями, событиями скролла, видео и GIF внутри страницы (`sr-browser/js/runtime.js`) и встроенный веб-сервер (`sr-site`).

### 7.4 Почему блоки на канвасе не полностью «живые» (ответ на R-22)

Идея: каждый блок на канвасе отрисовывает настоящий сайт в своих границах.

**Если сделать каждый блок живым** (отдельный встроенный браузерный фрейм на блок):
- **Нагрузка растёт, а не падает:** 15 блоков — это 15 копий всей страницы, каждая со всем своим JS, анимациями и видео.
- **Окно приложения рисует другой движок, чем запись:** на Linux интерфейс Tauri рисует WebKitGTK, а видео пишет Chromium. Блок на канвасе может выглядеть не так, как в видео.
- **Реальные сайты** (Webflow, Tilda — будущая цель) часто запрещают показ себя во фреймах.

**Принятый гибрид (D-05)** даёт ощущение живого сайта без этих минусов:
1. **Карточка блока** — точный срез из того же Chromium, что пишет видео. Это дёшево, и на канвасе ровно то, что попадёт в кадр.
2. **Инспектор** — рамки всех элементов приходят из браузера один раз. Подсветка элементов при наведении рисуется поверх снимка, без живого DOM.
3. **Live-блок** — один выбранный блок оживает: поток кадров из браузера-рендерера, анимации играют, hover работает. Нагрузка — один поток, сколько бы блоков ни было.
4. **Тайлы** — длинные страницы нарезаны на плитки с уровнями детализации (как карты), грузится только видимое.

## 8. Форматы файлов

### 8.1 Сценарий `*.srflow.json` — промо-видео

```json
{
  "$schema": "https://raw.githubusercontent.com/teplarium/ScrollRecord/main/schema/flow-v1.schema.json",
  "format_version": 1,
  "meta": { "name": "Acme landing promo", "site": "../site" },

  "targets": [
    { "id": "desktop", "viewport": "desktop-1920", "aspect": "16:9", "resolution": "1080p", "fit": "fill-viewport", "fps": 60, "format": "mp4" },
    { "id": "mobile",  "viewport": "iphone-15",    "aspect": "9:16", "resolution": "1080p", "fit": "fill-viewport", "fps": 60, "format": "mp4" }
  ],

  "defaults": {
    "scroll": { "speed_px_s": 900, "easing": "ease-in-out" },
    "hold_ms": 1500,
    "cursor": { "pack": "classic-light", "seed": 42, "visible": true }
  },

  "prepare": { "hide": [".dev-toolbar"], "preload_lazy": true, "wait": "network_idle" },

  "pages": [
    { "id": "home",    "url": "/" },
    { "id": "pricing", "url": "/pricing" }
  ],

  "nodes": [
    { "id": "start", "kind": "start", "at": { "block": "hero", "anchor": "top" } },

    { "id": "hero", "kind": "block", "page": "home",
      "target": [{ "sr": "hero" }, { "css": "section.hero" }],
      "align": "top", "hold_ms": 2000,
      "actions": [
        { "do": "hover", "target": [{ "role": "button", "name": "Get started" }], "duration_ms": 800, "mode": "real" },
        { "do": "click", "target": [{ "role": "button", "name": "Get started" }], "mode": "visual" }
      ]
    },

    { "id": "features", "kind": "block", "page": "home",
      "target": [{ "sr": "features" }], "hold_ms": 0 },

    { "id": "go-pricing", "kind": "navigate", "page": "home",
      "via": { "click": [{ "role": "link", "name": "Pricing" }] },
      "to_page": "pricing", "wait": "load" },

    { "id": "plans", "kind": "block", "page": "pricing",
      "target": [{ "sr": "plans" }, { "css": ".plans" }], "align": "center", "hold_ms": 2500,
      "actions": [
        { "do": "hover", "target": [{ "css": ".plan--pro" }], "duration_ms": 1200, "mode": "real" }
      ]
    },

    { "id": "end", "kind": "end", "at": { "block": "plans", "anchor": "center" }, "hold_ms": 1000 }
  ],

  "edges": [
    { "from": "start",      "to": "hero" },
    { "from": "hero",       "to": "features", "scroll": { "duration_ms": 1800 }, "cursor": "follow" },
    { "from": "features",   "to": "go-pricing" },
    { "from": "go-pricing", "to": "plans" },
    { "from": "plans",      "to": "end" }
  ],

  "overrides": {
    "iphone-15": {
      "nodes": {
        "go-pricing": { "before": [{ "do": "click", "target": [{ "css": "button.burger" }], "mode": "real" }] },
        "features":   { "skip": true }
      }
    }
  },

  "layout": { "...": "позиции и цвета фигур, только для редактора" }
}
```

**Действия и курсор (работают с Фазы 2):**
- `do`: `hover` (подвести и задержаться, по умолчанию 800 мс), `click`, `move` (к элементу или к точке блока `"to": {"x": 0.5, "y": 0.5}`), `wait` (`duration_ms`).
- `target` ищется сначала **внутри своего блока**: `{ "text": "Start" }` означает кнопку Start именно этого блока.
- `mode`: у `hover` по умолчанию `real`, у `click` — `visual` (безопасно: формы не отправляются).
- `delay_ms` — пауза перед действием; `only` / `except` — список id целей или пресетов устройства (`"only": ["desktop"]`).
- Блок с действиями всегда останавливает скролл, даже если `hold_ms: 0`. Остановка длится `max(hold_ms, время действий)`.
- `defaults.cursor`: `pack` (`classic-dark`, `classic-light` или папка пака), `scale`, `seed`, `visible`, `start` (точка старта, доли кадра), `speed`.
- `cursor` на стрелке: `still` (по умолчанию, мышь стоит), `follow` (едет вместе со страницей), `hide` (плавно исчезает на время скролла).

### 8.2 Сценарий — Block clip (запись анимаций)

```json
{
  "format_version": 1,
  "meta": { "name": "Hero + features animations", "site": "http://localhost:5173" },
  "targets": [
    { "id": "hero-loop", "viewport": "desktop-1920", "frame": "block", "frame_block": "hero",
      "resolution": { "scale": 2 }, "background": "transparent", "fps": 60, "format": "webm-alpha" }
  ],
  "defaults": { "cursor": { "visible": false } },
  "pages": [{ "id": "home", "url": "/" }],
  "nodes": [
    { "id": "start", "kind": "start", "at": { "block": "hero", "anchor": "top" }, "warmup_ms": 600 },
    { "id": "hero",  "kind": "block", "page": "home", "target": [{ "sr": "hero" }], "hold_ms": 4000 },
    { "id": "end",   "kind": "end",   "at": { "block": "hero", "anchor": "top" } }
  ],
  "edges": [{ "from": "start", "to": "hero" }, { "from": "hero", "to": "end" }]
}
```
*Вариант со scroll-анимацией:* `start.at = { block: "features", anchor: "enter" }` → `end.at = { block: "features", anchor: "exit" }`, на стрелке `scroll.duration_ms`, `frame_block: "features"`.

**Правила формата:**
- `target` — **список локаторов**. Берётся первый, который нашёл ровно **один** элемент. Если элементов несколько, выдаётся предупреждение. Приоритет в генераторе: `sr` (атрибут `data-sr="…"`, самый надёжный, его можно добавить в свой код) → `testid` → `id` → ARIA-роль + имя → видимый текст → CSS → `xpath` (крайний случай). Хэшированные классы (`css-1x2y3z`, `sc-…`) не используются.
- **Соглашение `data-sr` (D-16):** в коде своих сайтов блоки можно пометить `<section data-sr="hero">`. Имя — латиница в kebab-case, уникальное на странице. Метка необязательна: без неё работают остальные локаторы. Автопоиск блоков (FR-BLK-06) использует `data-sr` в первую очередь.
- Граф одного видео — **линейный путь** Start → … → End.
- `mode`: по умолчанию hover = `real`, click в блоке = `visual`, click в `navigate` = `real`.
- `targets[].aspect`: `16:9`, `9:16`, `1:1`, `4:5`, `4:3`, `3:4`, `2:3`, `21:9`, `native`, `{ "w": …, "h": … }`. Для `frame: block` пропорции берутся у блока.
- `targets[].resolution`: `720p`, `1080p`, `1440p`, `2160p` или `{ "scale": n }`.
- При изменении формата повышается `format_version`, старые файлы мигрируются автоматически.

### 8.3 Cursor pack (`*.srcursor` = zip или папка)

```
neon.srcursor/
├── cursor-pack.json
├── arrow.svg   pointer.svg   text.svg   touch.svg
└── preview.png              (необязательно)
```
```json
{
  "format_version": 1,
  "id": "neon", "name": "Neon", "author": "…", "license": "CC0-1.0",
  "states": {
    "arrow":   { "svg": "arrow.svg",   "hotspot": [3, 2],   "size": 32 },
    "pointer": { "svg": "pointer.svg", "hotspot": [10, 2],  "size": 32 },
    "text":    { "svg": "text.svg",    "hotspot": [16, 16], "size": 32 },
    "touch":   { "svg": "touch.svg",   "hotspot": [24, 24], "size": 48 }
  },
  "animations": {
    "click": { "keyframes": [{ "t": 0, "scale": 1 }, { "t": 80, "scale": 0.85 }, { "t": 220, "scale": 1 }], "easing": "ease-out", "effect": "ripple" },
    "hover": { "keyframes": [{ "t": 0, "rotate": 0 }, { "t": 150, "rotate": -8 }] },
    "idle":  { "frames": ["idle-1.svg", "idle-2.svg", "idle-3.svg"], "fps": 12, "loop": true }
  },
  "effects": {
    "ripple": { "color": "#FFFFFF80", "radius": 28, "duration_ms": 400 },
    "shadow": { "blur": 4, "opacity": 0.3 },
    "trail":  null
  }
}
```
- Анимации задаются **ключевыми кадрами** трансформаций (scale, rotate, opacity, offset) или **последовательностью SVG-кадров**.
- SVG должны быть статическими: без скриптов, без SMIL-анимаций, без внешних ссылок. Валидатор это проверяет.
- `hotspot` — точка «клика» в пикселях самого курсора (0…`size`), `size` — размер в CSS-пикселях при `scale: 1`.
- **Сделано в Фазе 2:** паки-папки, состояния `arrow` (обязательно), `pointer`, `text`, `touch` (если нет — стрелка и встроенный круг), `animations.click` (ключевые кадры), `effects.ripple`, `effects.shadow`. `animations.hover`, `animations.idle`, `effects.trail` и zip-файлы `.srcursor` пока принимаются с предупреждением, но не рисуются (MVP+).

## 10. Стандарт кода и комментариев

**Правило:** комментарий пишется на **смысловой блок** (функция, группа строк одной задачи, модуль) и отвечает на два вопроса: **зачем это нужно** и **какую проблему решает**. Построчные пересказы кода не пишутся. Язык комментариев — **английский**.

**Три уровня:**
1. **Шапка файла или модуля**: назначение, вход и выход, чего модуль *не* делает, связанные модули.
2. **Публичный API** (`///` в Rust, `/** */` в TS): что делает, какие ошибки возможны.
3. **Смысловые блоки внутри функций** (`// ── Title ──` + 1–3 строки «why / solves»).

**Rust:**
```rust
//! # sr-timeline
//! Purpose: turns the flow graph (blocks + arrows) into a frame-by-frame plan.
//! Solves:  rendering must be deterministic, so every scroll position and
//!          cursor point is computed up front, before the browser is touched.
//! Input:   `Flow` + measured block positions from `sr-analyzer`.
//! Output:  `Timeline` (one `FramePlan` per frame).
//! Does NOT: talk to the browser or draw anything (see sr-capture, sr-compositor).

// ── Graph → ordered path ────────────────────────────────────────────
// Why: users draw arrows in any order; recording needs one path Start → … → End.
// Solves: detects cycles/gaps and returns an error with the node id,
//         so the UI can highlight the broken node on the canvas.
fn linearize(flow: &Flow) -> Result<Vec<NodeId>, TimelineError> { /* … */ }
```

**TypeScript:**
```ts
/**
 * BlockCard — canvas node that shows one page section.
 * Why: users must see the real site content of a block, not an abstract box.
 * Solves: renders a cached slice (cheap) and switches to a live frame stream
 *         only when the user enables Live mode (one block at a time).
 */
export function BlockCard(props: BlockCardProps) { /* … */ }
```

**Прочие правила:**
- Rust: `cargo fmt`, `clippy -D warnings`, запрет `unwrap`/`expect` вне тестов. TS: `eslint` + `prettier`, строгий `tsconfig`, запрет строк, зашитых в JSX.
- В каждом crate и в каждой папке `features/*` лежит короткий `README.md`: назначение и как запустить тесты.
- Неочевидные решения записываются в `docs/adr/NNNN-title.md`.
- **Каждый фикс бага сопровождается тестом**, который падал до фикса.

## 11. Карта проекта (`PROJECT_MAP.md`)

Создаётся в Фазе 0 (на английском) и **обновляется в том же коммите**, где меняется структура.

**Содержание:**
1. Обзор за 30 секунд + схема потока данных.
2. Таблица модулей: модуль → назначение → ключевые файлы → точка входа (отдельно Rust-crates и фронтенд-features).
3. Индекс ключевых типов: `Flow`, `Node`, `Edge`, `Anchor`, `Locator`, `Target`, `Timeline`, `FramePlan`, `CursorPack`… → файл.
4. Карта IPC: Tauri-команда → Rust-функция → где вызывается во фронтенде.
5. **«Если сломалось X, смотри Y»:**

   | Симптом | Где смотреть |
   |---|---|
   | Видео дёргается / пропуски кадров | `sr-capture` (deterministic), шим времени |
   | Анимация блока не записалась / записалась не та | `sr-timeline` (якоря, warmup), `sr-capture` |
   | Блок не найден на мобилке | `sr-analyzer` (локаторы), overrides в сценарии |
   | Курсор не там / не тот вид | `sr-timeline` (траектории), `sr-cursor` |
   | Кривые пропорции или поля в видео | `sr-compositor` (fit, stage) |
   | Видео не кодируется | `sr-encoder`, лог ffmpeg в диагностике |
   | Канвас тормозит | `features/canvas` (тайлы), `sr-analyzer` (нарезка) |
   | Сайт из папки не открывается | `sr-site` (локальный сервер) |
   | Импорт от ИИ падает | `sr-core` (валидация), `schema/` |
   | Строка не переведена | `i18n/locales` |

6. Где лежат данные во время работы (настройки, кэш, логи, загруженные браузер и ffmpeg) на Windows и Linux.
7. Журнал структурных изменений.

`AGENTS.md` обязывает ИИ-ассистентов: читать `PROJECT_MAP.md` первым, соблюдать стандарт комментариев, обновлять карту, добавлять тест к каждому фиксу, гонять тесты затронутых модулей, не править сгенерированные файлы (`schema/`, `shared/ipc/`).

## 12. Работа без программиста: как ловить и чинить поломки

Владелец проекта не программист, а код пишут ИИ и контрибьюторы. Поэтому каждая проблема должна легко описываться и воспроизводиться.

| Механизм | Что делает |
|---|---|
| **Коды ошибок `SR-xxxx`** | Каждая ошибка в приложении показывает код и понятный текст. В `docs/ERRORS.md` для каждого кода описаны причина и что делать. По коду ИИ сразу находит место в коде |
| **Кнопка «Report a problem»** | Собирает zip: логи, сценарий, версии приложения, браузера, ffmpeg и ОС, снимок проблемного шага, последние кадры. Затем открывает страницу нового issue на GitHub с заполненными заголовком и окружением, остаётся приложить zip |
| **Формы issues на GitHub** | «Bug», «Site doesn't record correctly» (сайт или код + сценарий + что ожидалось), «Feature request», «Cursor pack». Человек отвечает на понятные вопросы, а не пишет с нуля |
| **CLI для воспроизведения** | `sr-cli render flow.json --target mobile --debug` повторяет проблему без интерфейса. Так ИИ проверяет фикс |
| **Обязательный CI** | Код не попадает в основную ветку, пока не прошли сборка, тесты и линтеры на Windows и Linux |
| **Регрессионные тесты** | Каждый фикс добавляет тестовую страницу или сценарий, на котором баг воспроизводился |
| **CHANGELOG простым языком** | Что исправлено и добавлено, понятно без знания кода |

### 14.1 Принятые идеи без фазы (владелец, 2026-10-26)
Владелец согласился, что это нужно сделать. Фазу выбирают, когда до идеи доходит очередь.

- **Сжатие видео на видеокарте, с запасным вариантом на процессоре.** Цель — рендер в 4K без перегрузки процессора.
  - Шаг 0: в отчёт рендера добавить время каждого этапа (Chrome, снимок, курсор, сжатие). Решать по цифрам: для Full HD сжатие `libx264 veryfast` сейчас, скорее всего, не самое узкое место. **Сделано 2026-10-28** (шаг 1c): `RenderReport.stages`, строки `stages:` в CLI.
  - **Замеры 2026-10-28** (ПК владельца: 12 логических ядер, RTX 3050, Chrome 155, ffmpeg 9.0.2; пример 01, MP4, 60 кадров/с, ~590 кадров ≈ 9,8 с видео; сборка release):

    | Цель | Всего | Скриншоты | Шаг страницы | Декод + курсор (параллельно) | Сжатие (ожидание ffmpeg) | Рендер ждал сжатие |
    |---|---|---|---|---|---|---|
    | desktop 1920×1080 | 84,8 с | 58,0 с | 25,8 с | 5,5 с | 0,9 с | 0,1 с |
    | mobile 1080×1920 | 76,5 с | 61,2 с | 14,9 с | 5,4 с | 0,9 с | 0,1 с |
    | desktop 3840×2160 | 121,5 с | 92,6 с | 27,7 с | 20,4 с | 3,1 с | 0,3 с |
    | mobile 2160×3842 | 130,0 с | 113,0 с | 16,3 с | 21,2 с | 3,2 с | 0,3 с |

    Сам ffmpeg (пересжатие этих видео, процессорное время без декодирования): Full HD `libx264 veryfast` ≈ 10 с процессора на ролик, 4K ≈ 41 с и ≈ 2,4 ГБ памяти; `h264_nvenc` — почти 0 с процессора. Во время 4K-рендера процессор занят в среднем ≈ 1,3 ядра из 12 (через 90 с: ffmpeg 48 с, главный процесс Chrome 31 с, ScrollRecord 21 с, GPU-процесс Chrome 17 с, вкладка 4 с).
  - **Вывод по цифрам:** сжатие на видеокарте рендер **не ускорит** — рендер почти не ждёт ffmpeg (≤ 0,3 с). Оно сняло бы самую большую нагрузку на процессор в 4K (≈ 40 % всей работы рендера и ≈ 2 ГБ памяти), но для «компьютер не тормозит» уже есть пониженный приоритет. Решение: отложить, не срочно. Главное время — скриншоты (⅔) и шаг страницы (⅓), а процессор почти свободен, поэтому сильнее всего ускорит **рендер нескольких целей одновременно** (desktop + mobile параллельно) — проверить в шаге 3.7 (очередь рендера). Ускорение самих скриншотов — отдельное исследование (уже включён самый быстрый режим Chrome, `optimizeForSpeed`).
  - Выбор кодировщика: пробное сжатие одного маленького кадра по очереди через `h264_nvenc` (NVIDIA), `h264_qsv` (Intel), `h264_amf` (AMD), иначе `libx264` (процессор). Результат запоминается. Настройка «авто / видеокарта / процессор».
  - По умолчанию H.264 (открывается везде). HEVC — опция («файл меньше»). AV1 умеют только RTX 40 и новее.
  - «Лучшее качество» остаётся на процессоре (`libx264 -preset slow`): на мелком тексте он чище.
  - Перевод цветов RGBA → YUV420p (BT.709) остаётся в ffmpeg перед любым кодировщиком (как сейчас в `sr-encoder` → `ffmpeg_args`), иначе цвета у видеокарты и процессора разойдутся.
  - Уточнить NFR-03: одинаковыми должны быть кадры. Байты MP4 на разных видеокартах и на процессоре будут разными.
  - У обычных видеокарт NVIDIA есть лимит одновременных сжатий (около 8 на свежих драйверах). Лишние задания сами уходят на процессор.
- **Пониженный приоритет рендера.** Chrome и ffmpeg запускаются с приоритетом «ниже среднего» (Windows: `BELOW_NORMAL_PRIORITY_CLASS`; Linux: `nice`), чтобы во время рендера компьютер не «задумывался». На повторяемость кадров это не влияет: рендер лишь идёт дольше. **Сделано 2026-10-28** (шаг 1c, ADR 0005): включено по умолчанию, `--normal-priority` выключает. На свободном компьютере скорость та же (83,6 с против 84,2 с), MP4 побайтно одинаковые. **Linux:** понижается только ffmpeg, Chrome остаётся с обычным приоритетом — запущенный через `nice` Chrome не успел стартовать за 30 с на Linux-машине GitHub (CI #11), а при полной загрузке процессора стартует в 4–6 раз медленнее; понизить приоритет уже после старта без небезопасного кода нельзя. Ограничение Windows: Chrome сам поднимает приоритет вкладки (обычный) и GPU-процесса (выше среднего), ключами запуска это не отключается; это ≈ 17 % работы 4K-рендера, а ffmpeg и главный процесс Chrome (≈ 65 %) остаются «ниже среднего». Опустить и их можно через Windows Job Object с лимитом приоритета (нужен доступ к WinAPI) — только если владелец заметит, что компьютер всё же тормозит.
- **Кеш с жёстким лимитом (коротко).** Для снимков страниц и тайлов в редакторе Фазы 3: свежие держатся в оперативной памяти с жёстким лимитом, остальные лежат на диске в папке проекта. RAM-диск не делаем: ему нужен отдельный драйвер с правами администратора, а Windows и так держит «горячие» файлы в памяти. Сам рендер промежуточных файлов не пишет: кадры идут из Chrome через память в ffmpeg.
- **Звук (Audio Pipeline), позже.** Сейчас звук вне MVP (§16), браузер работает с `--mute-audio`. Записать звук «с колонок» нельзя: рендер идёт медленнее реального времени. Правильный путь — собрать дорожку после рендера:
  - `<video>`/`<audio>` сайта: `runtime.js` уже знает, когда, с какого места и с какой скоростью играл каждый элемент. Основа — записывать эти события (файл, время страницы, позиция, скорость, громкость) в `timeline.json`, а ffmpeg потом смешает звук из исходных файлов.
  - Своя музыка или озвучка поверх видео — самое простое и, вероятно, самое нужное.
  - Звуки, которые сайт генерирует кодом (Web Audio), — сложно, отдельное исследование.
